# Day 27 — Capstone pt.1: Choose & Justify a Structure

> Week 4 · Capstone

## Learning objective

On a genuinely ambiguous problem you care about, **choose a lens (or sequence) and justify it** —
naming one rejected alternative — then build the structure with a template and pass the master
checklist. This is Day 27 of the capstone brief in `Capstone.md`; work that file as your spec.

## Minimum Viable Rep — 25 minutes
1. Produce the structure (the chosen-and-justified structure for your capstone problem).
2. Score it using the rubric.
3. Name one defect.
4. Repair one branch.
5. Write one sentence: "This structure helps because…"

## Concept lesson

The capstone removes the training wheels: no pre-chosen lens, no clean case — an open problem
where the *first* decision (how to cut it) is itself the test. Everything from Weeks 1–3 converges
here on one move: **choosing a structure on purpose and saying why.**

Run the **Day-21 diagnostic** (Field Manual §3) on your problem before reaching for a tool: Am I
explaining or choosing? Is there feedback / circular causality? Real uncertainty with payoffs? A
cleanly enumerable space? A hunch worth testing fast? Each strong "yes" points to a lens — and the
answer is often a *sequence* (process map to localize, then causal loop to explain).

The graded move is the **justification**: 3–4 sentences naming the lens, *why the problem's
features select it*, and **why you rejected the obvious alternative.** A lens you can't defend
against its rival is a reflex, not a choice. Then build with the matching template from
`Templates.md` and run the **§8 master checklist** — ME, CE, useful, decision-relevant, same
grain, right lens, hidden assumptions, no false categories. A capstone structure that fails the
checklist isn't ready to carry the analysis you'll do tomorrow.

## Practice case

Pick **one** ambiguous problem from `Capstone.md`'s brief: a real, currently-open problem from
your life (strongest — ECTango, ECOS/BRAIN architecture, a TTC board question, Neil outreach, an
IT client decision) or a multi-lens Case-Bank case (1, 11, or 16).

Decision-maker: **you, plus whoever you'd hand the eventual recommendation to** (the board, a
client, yourself). It must be genuinely unresolved — if you already know the answer, it's too easy;
pick something where the lens choice is live. The constraint against "gather more data": write the
problem as a one-paragraph situation a colleague would hand you, including the **decision that
hangs on it and the deadline** — so the structure has to serve a real choice, not an open-ended
study.

## Deliverable + Definition of Done

A chosen structure + a written justification, per the `Capstone.md` Day-27 spec: (1) Day-21
diagnostic answers; (2) named lens/sequence with 3–4 sentences of why, including one rejected
alternative; (3) the structure built in a `Templates.md` template; (4) the §8 checklist run on it.

**Definition of Done:** the structure passes the master checklist; the justification names at
least one rejected alternative and *why*; and you can state the **irreversible/reputation-sensitive
action the eventual recommendation will imply** (e.g., committing the board to a festival format,
re-architecting BRAIN's capture flow, advising a client to migrate) — so tomorrow's analysis is
aimed at a real decision, not a diagram.

## Self-check rubric

- [ ] I ran the Day-21 diagnostic and tied my lens to specific answers, not habit.
- [ ] My justification names a rejected alternative and why it loses.
- [ ] The structure is built in a matching template and passes the §8 checklist.
- [ ] The problem is genuinely ambiguous — I don't already know the answer.
- [ ] **What evidence, example, or counterexample would show this is incomplete, overlapping, or decision-irrelevant?** (e.g., a real case that won't file in any branch.)
- [ ] I can name the irreversible action the eventual recommendation will set up.

## Common mistake to watch for

**The reflexive MECE tree.** Defaulting to a tidy tree because trees feel safe — when the problem
has feedback (needs a loop) or real uncertainty with payoffs (needs a decision tree). The capstone
rubric weights *lens choice* precisely to catch this; a structure that's clean but wrong-shaped
fails the "right lens?" check no matter how MECE it is.

## When to use / when NOT to use

**Use** this full choose-and-justify discipline on any high-stakes, ambiguous problem where the
recommendation is irreversible or reputation-sensitive. **Don't** spend it on a problem whose shape
is obvious and whose cost of being wrong is trivial — there, just pick and move.

## Reflection question

Which lens did you *want* to use before you ran the diagnostic — and did the diagnostic confirm it
or override it? If it always confirms your first instinct, you may be reverse-justifying a reflex
rather than choosing.

## Optional stretch

Build a *second* structure for the same problem using the rejected lens. Lay them side by side.
Does the rejected lens reveal anything the chosen one hides? If so, your sequence may need both.
